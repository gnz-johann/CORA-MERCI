# Fase 1 · Bloque 1.0 · Sección 1.0.1 — Sincronizar `merci-platform` con `main` (corrige el informe de Fase 0)

## Qué se hizo
Se sincronizó el checkout local de `merci-platform` con el `main` real de GitHub (estaba
2 commits atrás) y se volvió a revisar si `src/modules/tickets/` existe. **Sí existe** — el
informe de Fase 0 (`INFORME_SITUACION_ACTUAL.md`) decía que no, y esa parte queda corregida
aquí. No se edita el informe viejo, como pide la regla del plan; este documento lo reemplaza
solo en ese punto.

## Por qué
El diagnóstico de Fase 0 se hizo contra un checkout de `merci-platform` que estaba parado en
el commit `b248dd3`. El `main` real de GitHub ya tenía 2 commits más (`3b5dac6` y `bce7e33`),
uno de los cuales agrega el módulo completo de tickets. Sin sincronizar primero, cualquier
decisión sobre "construir tickets desde cero" habría sido un error.

## Cómo
```bash
cd merci-platform
git fetch origin
git stash push -- .env.example package-lock.json   # ver "Pendiente/riesgos"
git pull origin main
git log -1 --oneline   # bce7e33 — confirmado
```

**Estado real de `src/modules/tickets/` (corrección al informe de Fase 0):**
Existe, con 4 archivos (`tickets.routes.js`, `.controller.js`, `.service.js`,
`.repository.js`) y 6 endpoints (`GET /catalogos`, `GET /`, `GET /:id`, `POST /`,
`POST /comentarios`, `PUT /:id`, `DELETE /:id`). Pero su estado real es más delicado de lo
que el plan asumía en el Bloque 2.3 ("toma `empresa_id` mal"):

- **`tickets.routes.js` no tiene ningún middleware — ni siquiera `authenticate`.** No hace
  falta estar logueado para usar estos endpoints.
- `tickets.controller.js` línea 11 toma `empresa_id` de `req.query` directo, sin pasar por
  `tenant.middleware`. Cualquiera que sepa o adivine un `empresa_id` puede leer o escribir
  tickets de esa empresa sin autenticarse.
- No hay ningún `requirePermission`.
- No llama a `audit()` — confirmado, tal como decía el plan.

Esto es, en los hechos, el mismo tipo de problema que la Sección 1.0.2 (agentes), pero más
grave porque aquí falta hasta el login. **No se corrigió en esta sección** — el alcance de
hoy (Bloque 1.0) era 1.0.1, 1.0.2, 1.0.3 y 1.0.4 según la instrucción recibida; Tickets no
está en esa lista. Queda anotado aquí para que el equipo decida si también amerita
tratamiento urgente en vez de esperar al Bloque 2.3.

## Archivos tocados
Ninguno de código. Este commit trae los 2 commits nuevos de `origin/main` (`3b5dac6`,
`bce7e33`) más este informe.

## Pendiente / riesgos
- **`git stash`**: antes de hacer `pull`, `merci-platform` tenía cambios sin commitear en
  `.env.example` (borrado) y `package-lock.json` (modificado, 640 líneas de diferencia). Se
  guardaron con `git stash` para poder hacer el pull limpio. El pull trajo, de forma
  independiente, el mismo borrado de `.env.example` — esa parte del stash ya no hace falta.
  `package-lock.json` sigue diferente y sigue guardado en el stash (`stash@{0}`), **sin
  aplicar** — el informe de Fase 0 ya señalaba que esto necesita que alguien del equipo
  confirme si el cambio local era intencional antes de decidir qué hacer con él. No se tocó
  más allá de guardarlo a salvo.
- **Tickets sin autenticación**: ver arriba. Riesgo real, no solo de diseño — hoy mismo
  cualquiera con la URL puede leer/crear/editar/borrar tickets de cualquier empresa sin
  loguearse. Se recomienda que el equipo decida si esto se trata con la misma urgencia que
  el Bloque 1.0 le dio a Agentes Virtuales (Sección 1.0.2).
