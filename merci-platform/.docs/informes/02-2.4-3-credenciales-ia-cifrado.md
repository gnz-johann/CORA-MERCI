# Fase 2 · Bloque 2.4 · Sección 2.4.3 — Cifrado real de `credenciales_ia`

## Qué se hizo
Se agregó `PUT /api/configuracion/credenciales-ia`, que cifra con AES-256-GCM (módulo
nativo `crypto` de Node, sin librerías externas) las claves de proveedores IA antes de
guardarlas en `configuraciones_empresa.credenciales_ia`. `GET /api/configuracion/empresa`
sigue sin devolver ese campo nunca (ya estaba excluido de `SELECT_SEGURO` desde la Sección
2.4.2). Con esto se cierra el Bloque 2.4 completo.

## Por qué
Se pidió explícitamente no repetir el patrón de `pbx.repository.js`: su comentario dice
"las credenciales se guardan encriptadas" pero el código real solo hace
`credenciales: datos.credenciales` tal cual llega — nunca se cifra nada, es una falsa
sensación de seguridad. Este módulo sí cifra de verdad.

## Cómo
- **`src/core/utils/credencialesIA.crypto.js`** (nuevo) — `cifrar()`/`descifrar()` con
  AES-256-GCM. Guarda un sobre `{ iv, authTag, ciphertext }` (todo en hex) en vez del valor
  plano. GCM valida el `authTag` al descifrar — un dato alterado o cifrado con otra clave
  lanza en vez de devolver basura silenciosamente.
- **La clave sale de `env.CREDENCIALES_IA_ENCRYPTION_KEY`** (32 bytes en hex, 64 caracteres),
  agregada como variable **requerida** en `src/config/env.js`, siguiendo la regla explícita
  del proyecto ("cuando agregues una env var requerida, agrégala a este schema").
- **`configuracionIA.repository.js`** — 3 funciones nuevas: `_obtenerConfigConCredenciales`
  (uso interno, incluye el sobre cifrado, nunca se manda al cliente — mismo prefijo `_` y
  mismo criterio que `pbx.repository.js._obtenerConfigConCredenciales`),
  `actualizarCredenciales` y `crearConCredenciales` (mismo upsert manual que el resto del
  módulo: si la empresa ya tiene fila en `configuraciones_empresa`, actualiza; si no, crea
  una nueva solo con `credenciales_ia`).
- **`configuracionIA.service.js`** — `guardarCredenciales()`: valida que el body sea un
  objeto plano, cifra, guarda, y llama a `audit.log()`. **Nunca escribe el valor real de una
  clave en el log de auditoría** — solo los *nombres* de las claves configuradas
  (`{ proveedoresConfigurados: ['openai_api_key'] }`), antes y después. Si loggeara el valor
  real, `GET /api/auditoria` (Sección 2.4.1) podría filtrar un secreto en texto plano a
  cualquiera con permiso `auditoria.ver`.
- Semántica **PUT = reemplazo completo**, no merge: mandar `{ credenciales: { openai_api_key: 'x' } }`
  reemplaza todo el objeto guardado, no lo combina con claves de otros proveedores guardadas
  antes. Es una decisión propia (el contrato no cubre este endpoint en absoluto, ver
  Sección 2.4.2) — documentada aquí por si el equipo prefiere merge en vez de reemplazo.
- Verificado con `node --check` en los 6 archivos tocados/creados.

## Pendiente / riesgos
- **El punto clave, y es grande: `AIProviderFactory.js:267` lee
  `config.credenciales_ia?.openai_api_key` directo, en texto plano, sin descifrar nada.**
  Está confirmado leyendo el archivo real, no es una suposición. Cifrar `credenciales_ia`
  desde este endpoint significa que, el día que alguien active Fase 5 (invocación real de
  IA), `AIProviderFactory` va a recibir el sobre cifrado `{iv, authTag, ciphertext}` como si
  fuera la API key, y va a fallar contra el proveedor real. `AIProviderFactory.js` es
  intocable por regla del plan ("Nunca tocar") y por regla del `CLAUDE.md` de este repo — no
  se le agregó descifrado. Esto es exactamente el tipo de cosa que el plan pide **no asumir
  y avisar**: la Fase 5 (fuera de este plan) va a necesitar que alguien agregue
  `credencialesCrypto.descifrar()` en el punto donde `AIProviderFactory` lee
  `credenciales_ia`, o el pipeline de IA en vivo seguirá roto aunque la clave esté guardada.
  No se resuelve aquí porque tocar ese archivo requiere aviso explícito y esta sección no lo
  tenía.
- **No se pudo agregar `CREDENCIALES_IA_ENCRYPTION_KEY` al `.env` real** — no tengo permiso
  para tocar ese archivo en esta sesión. Se generó una clave válida de 32 bytes:
  `88a6251915c6f4f905222d2c2f16b78e7db5d64db2ecdc185071b1e7baf6df48`
  (código, no secreto de producción — se puede regenerar con
  `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`).
  **Hasta que alguien agregue `CREDENCIALES_IA_ENCRYPTION_KEY=<esa clave>` a `.env`, el
  servidor completo no arranca** (`env.js` llama a `process.exit(1)`) — confirmado
  reproduciendo el error con `node -e "require('./src/routes/index.routes.js')"`. Esto no es
  exclusivo de este endpoint: bloquea Fase 3 (Bloque 3.3 necesita el servidor arriba). Nota:
  el log de arranque mostró `injected env ... encrypted .env [www.dotenvx.com]` — el `.env`
  de este proyecto está gestionado con dotenvx (formato cifrado), así que quien agregue la
  variable probablemente deba usar su flujo normal de dotenvx, no solo editar texto plano.
- Rotación de clave: si `CREDENCIALES_IA_ENCRYPTION_KEY` cambia alguna vez, todo lo ya
  guardado en `credenciales_ia` deja de poder descifrarse (el `authTag` no va a validar
  contra la clave nueva). No se construyó ningún mecanismo de rotación/versionado de
  clave — está fuera del alcance pedido, pero vale que el equipo lo sepa antes de rotarla en
  producción.
- No se probó contra Postgres real (Fase 3 no iniciada todavía) ni con una llamada HTTP real
  — solo `node --check` y el `require()` en frío que confirmó el bloqueo de arranque de
  arriba.
