# Fase 3 · Bloque 3.2 — Seed de datos de prueba realistas

## Qué se hizo
Se creó `prisma/seed.js`, que llena la BD local con una empresa de prueba aislada
("Empresa Demo Estabilización"), su sucursal, 2 usuarios (uno Admin General, uno Admin de
Sucursal) con sus roles asignados, 3 agentes virtuales, 5 llamadas y 3 tickets. Registrado
como `npm run db:seed` y como `prisma.seed` en `package.json` (soporta también
`npx prisma db seed`). Se corrió contra la BD local real y terminó sin errores.

## Por qué
Sin datos reales, ninguna vista puede probarse de verdad (Bloque 3.3 depende de esto). El
Bloque 3.1 (migrar con `prisma migrate dev`) quedó **pausado por decisión explícita tuya**
tras encontrar que la BD local ya tiene datos reales (2 empresas, 5 usuarios) pero
`prisma/migrations` está vacío — Prisma no la reconoce como gestionada por Migrate, y
`migrate dev` en ese estado puede ofrecer un reset completo. Se saltó directo a este bloque
sin tocar el estado de Migrate.

## Cómo
- **No reinventa lógica de negocio** — reutiliza los services reales del proyecto:
  `empresasService.crear()` (crea también los 2 roles por defecto vía
  `crearRolesDefault()`), `sucursalesService.crearSucursal()`, `usuariosService.crear()` +
  `.asignarRoles()` (mismo hash de password, misma validación que si se creara por la API),
  y `agentesService.crearAgente()`. Llamadas y tickets se crean con `prisma.*.create()`
  directo (no hay un "crear" reutilizable para llamadas de prueba — `llamadas.repository`
  solo expone `upsertLlamada`, pensado para eventos reales de CloudUCM).
- **No toca los datos ya existentes**: antes de escribir nada se verificó con un conteo
  (`empresas.count()`, `usuarios.count()`) que la BD ya tenía 2 empresas y 5 usuarios reales.
  El seed crea su propia empresa nueva, identificable por
  `nombre_comercial = 'Empresa Demo Estabilización'`, y no modifica ni borra nada fuera de
  ahí.
- **Guard de re-ejecución**: si esa empresa ya existe, el script sale temprano sin duplicar
  nada — verificado corriéndolo dos veces seguidas.
- **Bug encontrado y corregido durante la primera corrida real**: el tercer ticket (marcado
  como "Resuelto") violó el constraint `chk_ticket_fechas` de Postgres — `fecha_cierre` se
  calculaba con `new Date()` en el cliente antes del INSERT, mientras `fecha_creacion` usaba
  el default `now()` de la BD, que se ejecuta unos milisegundos después. Resultado:
  `fecha_cierre` quedaba (por milisegundos) antes que `fecha_creacion`. Se corrigió fijando
  `fecha_creacion` explícita en el propio JS para los 3 tickets, con `fecha_cierre` calculado
  con un margen de días, no milisegundos. Tras el error, se borró la empresa parcial creada
  (cascada automática vía `onDelete: Cascade`, no tocó las 2 empresas reales) y se corrió de
  nuevo limpio.
- **Detalle no obvio para arrancar el script**: desde la Sección 2.4.3, `src/config/env.js`
  exige `CREDENCIALES_IA_ENCRYPTION_KEY` y este seed importa `src/config/database.js` (para
  reusar los services reales), lo que dispara esa validación. El seed no cifra nada, así que
  al inicio del archivo se rellena esa variable con un valor de relleno **solo si no está
  definida ya** — nunca sobreescribe la real si el equipo ya la agregó a `.env`.

## Archivos tocados

- `package.json` (editado — `scripts.db:seed` + bloque `"prisma": { "seed": ... }`)

## Pendiente / riesgos
- **Bloque 3.1 sigue sin resolver, por tu decisión, no por omisión.** `prisma/migrations`
  sigue vacío; la BD sigue sin ser gestionada por Prisma Migrate. Falta decidir entre
  bautizar (baseline) el schema actual como ya aplicado —sin tocar ninguna fila— o algún
  otro camino, antes de poder decir que 3.1 está cerrado.
- Los 2 usuarios de prueba quedaron con password `Demo1234` en texto plano en este informe y
  en el `console.log` final del script — es intencional (son credenciales de un entorno de
  desarrollo local, para que cualquiera pueda usarlas en el Bloque 3.3), pero si este repo
  alguna vez deja de ser solo local, hay que rotarlas o borrarlas primero.
- El seed no crea nada para Auditoría (se llena sola vía `audit.log()` al crear las cosas de
  arriba — de hecho ya se generó un log real al crear los agentes), ni para
  `configuraciones_empresa`/`configuraciones_pbx` — esas se prueban en el Bloque 3.3
  llamando directamente a sus endpoints (`PUT`), no pre-sembrando filas.
- No se sembraron `departamentos` — Bloque 3.3 los prueba con la sucursal ya creada aquí
  (el endpoint de creación de departamentos existe y puede probarse en vivo).

## Pertenece a otra bina?
No — es infraestructura de prueba general del plan, no de un módulo de una bina específica.
Toca datos de Bina 1 (empresas/usuarios/roles/sucursales), Bina 2 (agentes) y Bina 3
(llamadas/tickets) solo para poblarlos con filas de prueba, sin cambiar ningún archivo de
esas binas.
