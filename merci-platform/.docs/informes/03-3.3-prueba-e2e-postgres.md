# Fase 3 · Bloque 3.3 — Prueba de punta a punta contra Postgres local

## Qué se hizo
Se levantó el servidor real (`node src/server.js`) contra la BD local y se probaron con
llamadas HTTP reales los 7 pares ya conectados: Auditoría, Configuración IA, PBX, Usuarios,
Roles, Sucursales y Departamentos — usando los 2 usuarios creados en el Bloque 3.2 (Admin
General y Admin de Sucursal de "Empresa Demo Estabilización"). No se tocó ningún archivo con
mock (`HistorialLlamadas.jsx`, `Configuracion.jsx`, etc. — eso es el Bloque 3.4, aparte).

## Por qué
Verificar con datos y una BD reales (no `node --check` en frío) que lo construido en el
Bloque 2.4 y lo ya existente de Bina 1/3 funciona de punta a punta, antes de tocar el
frontend en el Bloque 3.4.

## Cómo
- **El servidor no arrancaba** por la nueva variable requerida `CREDENCIALES_IA_ENCRYPTION_KEY`
  (Sección 2.4.3), que sigue sin poder agregarse a `.env` real (sin permiso para tocar ese
  archivo en esta sesión). Se arrancó con la clave inyectada solo en el proceso de esta
  prueba (`CREDENCIALES_IA_ENCRYPTION_KEY=<clave> node src/server.js`), sin escribir nada en
  `.env` ni en ningún archivo del repo — el servidor real sigue sin poder arrancar hasta que
  alguien del equipo agregue esa variable de verdad.
- Login real vía `POST /auth/login` con `usuario.general.demo`/`admin.sucursal.demo` +
  `codigoAcceso` de la empresa sembrada, para obtener JWT reales (no simulados).
- Resultados, endpoint por endpoint (todos con `200`/`201`/`403`/`404` — el código esperado
  en cada caso, no un 500 ni un crash):

  | Módulo | Prueba | Resultado |
  |---|---|---|
  | Auditoría | `GET /auditoria` | 200 — trae los logs reales que generó el Bloque 3.2 (creación de sucursal/usuarios/roles) |
  | Auditoría | `GET /auditoria/export` | 200 — CSV bien formado, `Content-Type: text/csv` |
  | Configuración IA | `GET /proveedores-ia` (y con `?tipo=stt`) | 200 — catálogo real, filtro por tipo funciona |
  | Configuración IA | `GET /empresa` antes de configurar | 200, `data: null` (como se diseñó en la Sección 2.4.2) |
  | Configuración IA | `PUT /empresa` | 200 — crea la fila, devuelve camelCase correcto |
  | Configuración IA | `PUT /credenciales-ia` | 200 — cifra y guarda, responde solo `{proveedoresConfigurados:['openai_api_key']}` |
  | Configuración IA | `GET /empresa` después de guardar credenciales | **`credenciales_ia` nunca aparece en la respuesta** — confirmado programáticamente, no solo a ojo |
  | PBX (Bina 3) | `GET /configuracion/pbx` sin configurar | 404 `NotFoundError` — el módulo de Bina 3 sigue intacto y funcionando |
  | Usuarios | `GET /usuarios`, `GET /usuarios/:id` | 200 ambos |
  | Roles | `GET /roles` | 200 — trae "Administrador de Sucursal"; **"Administrador General" no aparece**, confirmando que el filtro `es_protegido` de `roles.repository.js` funciona de verdad, no solo en teoría |
  | Sucursales | `GET /sucursales` | 200 |
  | Departamentos | `GET /departamentos` (Admin General) | **403** — esperado: `departamentos.*` está excluido del rol Admin General por diseño (`sucursalId` null) |
  | Departamentos | `GET`/`POST /departamentos` (Admin Sucursal) | 200/201 — lista, crea uno de prueba, vuelve a listar y aparece |

- **Bonus no pedido explícitamente pero relevante**: se aprovechó tener los 2 roles reales
  para confirmar el aislamiento cruzado — el Admin de Sucursal recibió `403` al llamar
  `GET /auditoria`, `GET /configuracion/empresa` y `GET /sucursales`, exactamente los
  permisos que `PERMISOS_EXCLUIDOS_ADMIN_SUCURSAL` (`empresas.repository.js`) dice que debe
  excluir. Confirma en vivo, no solo leyendo código, que esa lista realmente se aplica.

## Pendiente / riesgos
- **La prueba dejó datos reales dentro de "Empresa Demo Estabilización"** (la misma empresa
  aislada del Bloque 3.2, no las 2 empresas reales): una fila en `configuraciones_empresa`
  (con `credenciales_ia` cifrado con una clave de prueba `sk-test-solo-para-e2e-no-es-real`,
  **no una clave real de OpenAI**) y un departamento "Departamento Demo E2E". Se dejaron a
  propósito — hacen que la empresa de prueba quede más completa para el Bloque 3.4, en vez de
  revertir el único configuracion/departamento que existía para probar.
- **Sigue sin resolverse el bloqueo de `.env`** (ver Sección 2.4.3): el servidor real, sin la
  variable inyectada manualmente como se hizo aquí, no arranca. Cualquier prueba futura (o el
  propio Bloque 3.4, si necesita el servidor arriba) va a tropezar con lo mismo hasta que
  alguien del equipo agregue `CREDENCIALES_IA_ENCRYPTION_KEY` a `.env` de verdad.
- No se probaron Auditoría/ConfiguraciónIA/PBX/Usuarios/Roles/Sucursales/Departamentos en
  **todas** sus variantes (ej. editar/eliminar en cada uno, o filtros de auditoría por fecha)
  — se probó el camino principal de cada endpoint pedido, no una batería exhaustiva.
- El servidor de prueba se apagó al terminar esta sección (`pkill`) — no queda corriendo en
  segundo plano.
